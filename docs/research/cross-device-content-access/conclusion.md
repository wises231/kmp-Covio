# 跨设备内容读取结论与限制

> 本文件承载结论摘要、决策因素、决策表、限制和不采用方案。

## 1. 结论摘要

安装 Covio 之后，三类内容的可读性分两层。

本机读取层：
桌面端三类内容都可以读。
macOS 和 Windows 的剪切板无需授权。
Windows 的截图目录无需授权。
macOS 的截图目录需要一次文件夹授权。
移动端只有前台可读。

跨设备读取层：
拉取模型在移动端不成立。
推送模型是唯一覆盖四个平台的路径。
桌面到桌面可以做到常驻自动。
移动端需要用户动作或系统唤醒。

系统原生能力覆盖同生态场景。
通用剪贴板、隔空投送、快速分享和就近共享都要求同账号或同生态。
跨生态组合没有被原生能力覆盖。
此处是 Covio 的增量空间。

结论按证据编号引用 [evidence.md](evidence.md)。

## 2. 决策因素

### 2.1 主要因素

**F1：移动端后台不能读取内容。**
iOS 后台执行本地网络操作时被直接拒绝且不补弹提示（`E-13`）。
iOS 的后台监听 socket 没有契约保证（`E-15`）。
Android 在 Doze 状态下暂停网络访问（`E-23`）。
三台证据合并的推论是：移动端不能作为被动接收方。

**F2：Android 剪切板只对焦点应用开放。**
Android 10 起非焦点应用读不到内容（`E-18`）。
变更监听器对不合格应用不触发（`E-18`）。
写入不受限制，读取受限（`E-18`）。
符合条件的常驻读取方只有默认输入法。

**F3：iOS 剪切板内容读取需要用户动作。**
程序化读取会弹出确认提示（`E-10`）。
免提示的接口不返回内容（`E-10`）。
唯一免提示的内容通道需要用户点击控件（`E-10`）。

**F4：设备发现需要新的授权与声明。**
Apple 平台需要 `NSLocalNetworkUsageDescription` 与 `NSBonjourServices`（`E-13`）。
iOS 上使用任意 Bonjour 服务类型需要向 Apple 申请组播权限（`E-14`）。
Android 17 起本地网络访问需要运行时权限（`E-22`）。
Windows 有原生 DNS-SD，但首次监听触发防火墙提示（`E-28`）。
标准用户无法为入站监听创建允许规则（`E-37`）。
五款主流局域网应用都不用系统 DNS-SD 接口（`E-38`）。

### 2.2 次要因素

**F5：macOS 剪切板闸门正在成形。**
系统已提供访问行为查询接口（`E-07`）。
系统设置里已出现剪切板访问面板（`E-05`）。
开发者预览开关在 macOS 27.2 被移除（`E-07`）。
当前默认仍为允许，但不能假设长期成立。

**F6：ad-hoc 签名会破坏授权身份。**
本地网络授权和 TCC 都按代码签名识别程序（`E-16`）。
内测构建每次重建都可能要求用户重新授权（`E-16`）。

**F7：四个平台都没有截图事件接口。**
macOS 只有落盘后的元数据属性（`E-08`）。
iOS 的通知只在应用运行时触发（`E-12`）。
Android 的检测接口只覆盖自身界面（`E-21`）。
Windows 没有观察接口，只有自身发起的协议（`E-27`）。

**F8：Windows 截图协议要求打包身份。**
`ms-screenclip://` 的响应只能回传给打包应用（`E-27`）。
非打包调用方拿不到截图结果（`E-27`）。

**F9：6 位短码的熵不足以单独承担配对。**
6 位短码只有 20 位熵（`E-35`）。
成熟方案使用 PAKE 或二维码携带公钥（`E-35`）。

**F10：Windows 的常驻能力受账户权限与快速启动限制。**
标准用户无法为入站监听创建允许规则（`E-37`）。
注销终止登录会话内的全部进程（`E-39`）。
快速启动是注销，托盘应用不存活（`E-39`）。
因此快速启动后的设备应按离线处理。
常驻接收方需要会话 0 服务，或需要用户重新登录。

## 3. 决策表

| 决策 | 选择 | 原因 | 备选路径 |
| --- | --- | --- | --- |
| 传输模型 | 推送为主，拉取仅用于桌面常驻对等端 | 移动端拉取被系统限制否决（F1、F2、F3） | 全平台拉取，不可行 |
| 移动端触发方式 | 用户动作或系统唤醒后拉取 | 后台读取不可用（F1） | 常驻监听，不可行 |
| 剪切板策略 | 桌面常驻监听，移动端前台读取 | 桌面无限制，移动端受限（F2、F3） | 移动端全自动同步，不可行 |
| 截图策略 | 目录监视加相册读取，移动端补分享面板入口 | 没有事件接口（F7） | 轮询相册，耗电且不可靠 |
| 发现机制 | mDNS 为主，自定义组播为辅，二维码与短码兜底 | 四个平台的授权与能力不同（F4） | 只用 mDNS，Android 与 Windows 上风险高 |
| Windows 常驻方式 | 托盘应用为主，会话 0 服务作为可选增强 | 标准用户与快速启动限制（F10） | 只靠托盘应用，快速启动后不可用 |
| Windows 入站放行 | 安装时引导管理员放行，或改用出站连接 | 标准用户无法创建允许规则（F10） | 依赖首次监听提示，标准用户下失败 |
| 配对方式 | 二维码携带公钥为主，短码为辅并限速 | 短码熵不足（F9） | 只用短码，需要 PAKE |
| 签名策略 | 发布构建使用稳定签名，内测说明授权会失效 | 签名决定授权身份（F6） | 保持 ad-hoc，用户体验受损 |
| 平台范围 | 桌面端提供完整能力，移动端提供前台与分享能力 | 能力边界由系统决定 | 四端一致，不可行 |

## 4. 逻辑证据链

### 4.1 观察一：桌面端本机读取无授权门槛

观察：macOS 与 Windows 的剪切板读取都不需要授权（`E-02`、`E-24`）。
观察：Windows 的截图目录按已知文件夹访问（`E-26`）。
推论：桌面端可以做到常驻自动收集。
置信度：高

### 4.2 观察二：移动端读取被会话限制

观察：iOS 后台本地网络操作被直接拒绝（`E-13`）。
观察：Android 后台读不到剪切板（`E-18`）。
观察：Android 在 Doze 下断网（`E-23`）。
推论：移动端不能作为被动接收方。
推论：移动端只能主动推送。
置信度：高

### 4.3 观察三：跨设备产品全部采用推送或被同步

观察：KDE Connect 的手机到电脑剪切板同步因 Android 限制失效（`E-31`）。
观察：Syncthing 用双方确认的持续同步实现准拉取（`E-32`）。
观察：LocalSend 不做配对，只做接收确认（`E-30`）。
推论：推送模型与现有实践一致。
置信度：高

### 4.4 观察四：发现机制必须分层

观察：Apple 平台需要声明具体服务类型（`E-14`）。
观察：Android 17 需要新的运行时权限（`E-22`）。
观察：Windows 原生支持 DNS-SD（`E-28`）。
推论：单一发现机制无法覆盖四个平台。
推论：需要二维码或短码作为兜底。
置信度：高

## 5. 不采用方案

| 方案 | 风险 |
| --- | --- |
| 全平台拉取 | 移动端系统限制导致不可实现（F1） |
| Android 无障碍服务读取剪切板 | AOSP 无豁免，且商店政策限制（`E-19`） |
| 透明 Activity 抢占焦点读取剪切板 | 触发系统提示，与被处罚的隐蔽读取模式相同（`E-19`） |
| 云端中继 | 违反产品约束"不建立云端内容存储" |
| 依赖系统原生通道 | 跨生态不可用（`E-33`） |
| Bonjour 通配服务类型 | iOS 需要组播权限，批准由 Apple 决定（`E-14`） |
| 移动端常驻前台服务接收 | 不符合商店对前台服务的政策取向（`E-36`） |

## 7. 限制和未决项

### 7.1 系统限制

1. 移动端后台不能读取内容。
2. Android 的剪切板读取需要焦点或默认输入法身份。
3. iOS 的剪切板内容读取需要用户交互。
4. 四个平台都没有截图事件接口。
5. 本地网络访问需要授权，且发现可能需要前台。

### 7.2 产品限制

1. 移动端无法做到无感自动同步。
2. 跨生态场景需要自建传输通道。
3. 内测分发方式会削弱授权稳定性。
4. 截图收集依赖目录或相册授权，用户拒绝后能力消失。

### 7.3 未决项

1. 移动端后台行为的真机验证结果。
2. macOS 27 公证应用上剪切板闸门的默认值。
3. 组播权限的申请周期与批准标准。
4. Android 17 的发布时间表与 Play 强制时间点。
5. 厂商定制系统的截图路径与后台策略差异。
6. 是否值得增加持续文件夹同步作为可选能力。
7. Windows 标准用户在管理员预先放行后的实际行为。
8. Windows 会话 0 服务提升到用户界面的可用性。
9. Android 快速分享与 Windows 就近共享的互通状态。
