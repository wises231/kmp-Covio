# 路线图文档编写规范

## 文档状态

| 项目 | 内容 |
| --- | --- |
| 文档版本 | `1.0` |
| 状态 | 待评审 |
| 日期 | `2026-10-13` |
| 适用对象 | 产品、研发、测试和自动化 agent |
| 适用范围 | `docs/roadmap/` 下路线图文档、阶段表和 issue 定义文件的格式与模板 |

本文定义路线图和 issue 定义文件的格式与模板。
本文不定义立项、排期、收口和变更的流程。流程见 [../workflow/roadmap-first.md](../workflow/roadmap-first.md)。
本文不定义工作类型的划分。工作类型见 [../workflow/work-types.md](../workflow/work-types.md)。

## 1. 适用范围

本文适用于以下文件。

- `docs/roadmap/README.md`，路线图归档索引。
- `docs/roadmap/<slug>.md`，一份路线图。
- `docs/roadmap/issues/<本地编号>-*.md`，issue 定义文件。

本文不适用于以下内容。

- `docs/covio-product-master.md` 的产品路线图。它与 `docs/roadmap/` 是两套东西。
- `docs/covio-macos-swiftui-migration-plan.md` 的迁移阶段。它用 `M<n>` 编号。
- `docs/research/AUTHORING.md` 的研究流程阶段。那些是研究步骤，不是交付阶段。

## 2. 命名格式总表

| 对象 | 格式 | 正则 | 示例 |
| --- | --- | --- | --- |
| 路线图文件名 | `<slug>.md` | `^[a-z0-9-]+\.md$` | `curtain-workbench.md` |
| 阶段编号 | `P<n>` | `^P[0-9]{1,2}$` | `P2` |
| milestone 标题 | `P<n> · <阶段名称>` | `^P[0-9]{1,2} · .+$` | `P2 · 工作区模型` |
| 阶段 label | `phase-<n>-<slug>` | `^phase-[0-9]{1,2}-[a-z0-9-]+$` | `phase-2-workspace-model` |
| epic 本地编号 | `E<nn>` | `^E[0-9]{2}$` | `E03` |
| sub-issue 本地编号 | `E<nn>-S<nn>` | `^E[0-9]{2}-S[0-9]{2}$` | `E03-S02` |
| issue 定义文件名 | `<本地编号>-<slug>.md` | `^(E[0-9]{2}(-S[0-9]{2})?)-[a-z0-9-]+\.md$` | `E03-S02-workbench-store.md` |
| 计划的阶段编号 | `M<n>` | `^M[0-9]{1,2}$` | `M3` |

milestone 标题的分隔符是 U+00B7 中点，两侧各一个半角空格。
不要用 U+2022 圆点、U+30FB 片假名中点，或两侧没有空格的 U+00B7。

阶段 label 的颜色固定 `C5DEF5`。
阶段 label 的描述格式是 `阶段 <n> · <阶段名称>`。

阶段编号和本地编号都只在所属路线图内唯一。
一个路线图一个编号命名空间。

## 3. 路线图文档结构

一份路线图用以下 12 节。节号固定，不得增删节。

| 节 | 标题 | 必填 |
| --- | --- | --- |
| 文档状态 | 文档状态 | 是 |
| 1 | 结论摘要 | 是 |
| 2 | 需求拆解 | 是 |
| 3 | 现状基线 | 是 |
| 4 | 命名决策 | 否 |
| 5 | 目标架构 | 是 |
| 6 | 阶段与里程碑 | 是 |
| 7 | Epic 与 sub-issue 索引 | 是 |
| 8 | 依赖关系 | 是 |
| 9 | 风险与未决项 | 是 |
| 10 | 不在范围内 | 是 |
| 11 | 验收标准 | 是 |
| 12 | 用法 | 是 |

### 3.1 文档状态

用表格。字段固定。

| 项目 | 内容 |
| --- | --- |
| 文档版本 | `<主版本>.<次版本>` |
| 状态 | 待评审、可评审或已结案 |
| 日期 | `<YYYY-MM-DD>` |
| 适用对象 | 读这份文档的角色 |
| 适用范围 | 平台或模块边界 |
| 当前基线 | 版本号和分支 |
| 交付物 | 本文档和配套文件 |
| 上游文档 | 相对路径链接 |

### 3.2 第 1 节 结论摘要

用不超过 12 句话说明这份路线图要做什么。
第一句写目标。
最后三句写范围边界和规模。

**禁止在第 1 节枚举阶段名称。**
阶段的唯一真相是第 6 节的表。
两处枚举会互相矛盾。

规模写成「本路线图共 N 个 epic 和 M 个 sub-issue」一句。
不要用另一种说法重复阶段数量。

### 3.3 第 2 节 需求拆解

用表格。字段固定。

| 序号 | 需求 | 能力 | 现状 |
| --- | --- | --- | --- |

序号用 `R1`、`R2`。
「能力」写产品能力，不写技术手段。
「现状」写「无」「部分」或现有实现的位置。

### 3.4 第 3 节 现状基线

列出本次改造要动到的现有代码。
每条写路径、行号和一句说明。
路径相对仓库根目录。

**禁止写本机绝对路径。**

### 3.5 第 4 节 命名决策

只有存在名称冲突时才写这一节。
用表格列出概念、代码标识符、中文名和说明。
表后加一句警告，说明容易混用的两个词。

### 3.6 第 5 节 目标架构

按层写。每层一个小节。
每层列出类型名和职责，不写实现细节。
需要更细的说明时，链接到 `docs/design/` 下的文档。

### 3.7 第 6 节 阶段与里程碑

格式见第 4 节。

**这一节是阶段的唯一真相。** 其他节不得复制阶段名称或阶段数量。

### 3.8 第 7 节 Epic 与 sub-issue 索引

用表格。字段固定。

| 编号 | 标题 | 阶段 | 子项数 |
| --- | --- | --- | --- |

**禁止在第 7 节加进度列。**
进度由 GitHub 上 sub-issue 的实际状态推导。见 [../workflow/roadmap-first.md](../workflow/roadmap-first.md) 第 4 节。

### 3.9 第 8 节 依赖关系

用 ASCII 图表示 epic 之间的依赖。
箭头方向是「被依赖 → 依赖」。
图后写关键路径，用一句 `A → B → C` 的形式。
写明哪些 epic 贯穿全程但不阻塞功能开发。

### 3.10 第 9 节 风险与未决项

分三节：阻断级风险、一般风险、未决项。

阻断级风险用小节标题加粗编号，形如 `**U-01：<标题>**`。
一般风险用表格，字段是编号、风险、缓解。编号用 `R-01`。
未决项用有序列表。

结论已出的风险要写明结论日期和证据链接。

### 3.11 第 10 节 不在范围内

用无序列表。
每条写范围外的事项和原因或指向。

### 3.12 第 11 节 验收标准

用有序列表。
每条必须可判定。
最后三条固定是测试命令、合同校验命令和文档同步。

### 3.13 第 12 节 用法

写怎么用 `issues/` 目录和创建脚本。
包含 `--dry-run` 预览命令和正式创建命令。
包含公开仓库警告。

## 4. 阶段表模板

第 6 节的表头固定为五列。

```markdown
## 6. 阶段与里程碑

milestone 的标题格式是 `P<n> · <阶段名称>`。一个阶段对应一个 milestone。

| 阶段 | 阶段名称 | label | 目标 | 退出条件 |
| --- | --- | --- | --- | --- |
| P0 | 调研与决策 | `phase-0-research` | 判定手势入口可行性 | 两份调研结论和两份 ADR 通过评审 |
```

字段规则：

| 列 | 内容 |
| --- | --- |
| 阶段 | 阶段编号，形如 `P0`。 |
| 阶段名称 | 阶段的中文名。也是 milestone 标题里 `P<n> · ` 之后的部分。 |
| label | 阶段 label，用反引号包住。 |
| 目标 | 这一阶段要达成的结果。一句话。 |
| 退出条件 | 判定这一阶段完成的证据。可判定。 |

**不要加「里程碑」列。** 里程碑是阶段的投影，不是第二个概念。
**不要加「进度」列。** 进度从 GitHub 推导。

## 5. issue 定义文件格式

每个文件用 YAML front-matter 描述元数据，正文就是 issue 正文。

```yaml
---
id: E01-S02
title: "触控板四指下滑触发"
labels: [enhancement, phase-1-curtain-core, area/trigger]
type: Task
parent: E01
milestone: "P1 · 挂帘内核"
blocked-by: [E00-S01, E01-S01]
---
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | issue 的本地编号。`E00` 是 epic，`E00-S01` 是 sub-issue。 |
| `title` | 是 | issue 标题。 |
| `labels` | 是 | 标签列表。脚本会自动创建缺失的标签。 |
| `type` | 否 | GitHub issue type。脚本传给 `gh issue create --type`。 |
| `parent` | 是 | 父 issue 的本地编号。epic 写 `null`。 |
| `milestone` | 否 | 里程碑名。脚本会自动创建缺失的里程碑。 |
| `blocked-by` | 否 | 阻塞本 issue 的本地编号列表。 |

`type` 的可选值见 [work-types.md](../workflow/work-types.md)。
自定义类型由 `scripts/sync-issue-types.sh` 创建。
`type` 缺字段时脚本不传 `--type`。账号里没有自定义类型时脚本照样能跑。
账号没有对应类型时 `type` 字段静默失效。见 [work-types.md](../workflow/work-types.md) 第 1.4 节。

`milestone` 的值必须匹配第 2 节的 milestone 标题格式。
`labels` 里的阶段 label 必须匹配第 2 节的阶段 label 格式。

## 7. 更新规则

| 时机 | 改什么 |
| --- | --- |
| 立项 | 建 `<slug>.md`，在 `README.md` 主题索引加一行。 |
| 执行阶段 | 不改路线图。进度从 GitHub 推导。 |
| 阶段收口 | 改 `README.md` 主题索引的状态列。 |
| 新增或关闭 issue | 改路线图第 7 节的索引。 |
| 改 issue 正文 | 同步改路线图对应节。 |
| 改阶段 | 第 2、6、7、8 节一起改，文档版本号加一。 |
