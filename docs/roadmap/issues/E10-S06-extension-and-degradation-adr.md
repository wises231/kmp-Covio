## 背景

骨架第 9 节写了三类扩展点、三条降级路径，以及一条明确的否定：
「不为扩展点预留抽象接口。加平台时再抽」。

这条否定与 `E00-S04` 的验收第 3 条冲突。
`E00-S04` 要求 `ADR-003` 明确写出 Windows 与 iOS 如何接入同一协议。
写出接入路径，通常意味着协议要为未实现的平台留出形状。

两处对「要不要预留接口」的结论相反。路线图第 9.1 节的 `U-04` 登记了这个冲突，归本条裁决。

降级路径另有一处需要接上。
骨架第 9 节说「降级对用户可见。降级发生时，外壳不显示错误面板，只在设置页记录」。
记录的位置、格式和用户如何看到，没有定。

## 待决策

1. 是否为扩展点预留抽象接口。骨架第 9 节说不预留，`E00-S04` 验收第 3 条要求写出接入路径。
2. 若不为扩展点预留接口，`ADR-003` 如何写出 Windows 与 iOS 的接入路径。
3. 三条降级路径的用户可见性：在哪里记录，用户怎么看到。
4. 降级记录的格式与保留期。
5. 「新增一个平台」的最小改动集，以及它是否可验证。

## 候选方案

### 方案 A：不预留，按骨架第 9 节的原文

加平台时再抽。`ADR-003` 不写接入路径。

代价：`E00-S04` 验收第 3 条落空，需改写该条。
适用条件：接受「没有第二个平台就不抽象」。

### 方案 B：预留平台适配层

在 `CurtainTrigger` 之外再抽一层平台适配接口。

代价：违反骨架第 9 节。当前没有第二个平台可以验证这层抽象，抽象的形状只能靠猜。
适用条件：第二个平台的接入方式已经明确。

### 方案 C：不预留代码接口，但要求写接入路径

`ADR-003` 用文字写出 Windows 与 iOS 接入同一协议的步骤，不要求代码里出现新抽象。

代价：接入路径是文档承诺，没有编译期约束。承诺会随代码漂移。
适用条件：`E00-S04` 验收第 3 条要的是「写清楚」，不是「写出来能编译」。

## 判定依据

1. `E00-S04` 验收第 3 条能否满足，或能否按结论改写。
2. 不引入无法验证的抽象。这是骨架第 9 节否定的理由。
3. 新增平台的最小改动集能在文档里写清。
4. 降级对用户可见，且不打断当前操作。
